## Defects found by review and deliberately not fixed in place

Each of these is reproduced and understood. None is left open because it
is hard; each is left open because closing it is a design decision that
belongs to a review rather than to the change that found it.

| ID | Defect | Why it is not fixed here |
| --- | --- | --- |
| review-2 | CLOSED. Every request that reached the matcher through the Next.js route arrived from one loopback socket, because `matcher-proxy.ts` forwarded no client identity, so all callers shared one rate-limit bucket. The trusted-proxy arrangement is now implemented: the proxy proves its hop with an operator-configured key (`PHLEBAS_MATCHER_PROXY_KEY`) and forwards the edge-established client identity in a dedicated header; the matcher (`PHLEBAS_MATCHER_TRUSTED_PROXY_KEYS`, bounds-checked at startup) raises the per-client identity for both of its limiters only when the hop key matches, and compares keys by SHA-256 digest in constant time. With no key configured, nothing changes: the identity remains the socket address and unbounded or control-bearing forwarded identities fail closed. The pairing contract is in `docs/OPERATIONS.md`; the deploy-time key is stored in the operator vault, not in the repository. | Closed. |
| review-3 | CLOSED. `detectAlerts` compared a duration in seconds against `config.reorgDepth`, a count of blocks. The field is now `reorgWindowSeconds`, read from `PHLEBAS_OBSERVER_REORG_WINDOW_SECONDS`, and is deliberately not derived from the block depth: that conversion needs a per-chain block interval, and the observer watches two chains that do not share one. Choosing the number is a deployment decision, and stating it in the right unit is what this row was actually about. | Closed. |
| review-4 | `swap-state.ts` can only clear a dispute whose reason is `reorganization`, and only when it is the sole dispute on the swap. `observer-conflict`, `observer-stale` and `semantic-mismatch` have no resolution transition at all, so two approved observers disagreeing once leaves the coordinator permanently unable to observe or confirm anything further on that swap, refunds included. The wallet-controlled refund on the chain itself is unaffected. | This may well be the intended fail-closed behaviour. Adding a transition that clears a dispute is adding authority to the settlement state machine, which `CONTRIBUTING.md` puts behind an architecture decision and an independent review. |
| review-7 | A `ZecWalletSession` has no invalidation path. `evm-wallet-session.ts` exports `subscribeReviewedWalletSession`, which tears a reviewed session down on `accountsChanged`, `chainChanged` or `disconnect`. The ZEC session has no equivalent, so once connected it goes on asserting that the address it proved control of is the active one, and `landing-wallet-connect.tsx` holds it as plain React state with no listener. A user who switches accounts in their wallet leaves a session whose `addressControlSignature` proves control of an address they are no longer using. | Not deferred for effort. `ZecJsonRpcProvider` is `{ request }` and nothing else: Zcash browser wallets have no EIP-1193-style event surface to subscribe to, as `zec-wallet-provider.ts`'s own header records. The alternative is re-querying `zcash_accounts` on a schedule, and how often a page should interrogate a wallet is a product decision, not one this row should make. |

## Defects closed by consolidation

| ID | Defect | How it was closed |
| --- | --- | --- |
| review-5 | `src/lib/order.ts` still exposed `calculatePreviewNotional` and the float worst-price path used by market orders, after the settled-amount preview moved to exact integers. A sweep demonstrated the float worst price could disagree with the signed `worstPriceTicks` by one tick at extreme slippage, where float error escapes the rounding tolerance. | The market-order worst-price preview now parses slippage and computes the price through the exact primitives the submission path uses (`parseAtomicUnits` and `worstPriceTicks`), so the displayed worst price is the price the order signs. `calculatePreviewNotional` and `calculateWorstPrice` were deleted with their float constants; one implementation of each primitive remains. The previously divergent inputs are pinned to the exact answers in `units.test.ts`. |
| review-1 | `maximumAcceptedOrders` bounded a set that was only ever added to, so it was a lifetime quota rather than a live-capacity limit: once the configured number of orders had ever been accepted, the market accepted nothing further, and journal replay rebuilt the condition so it survived restart. | CLOSED. ADR 0010 is accepted and both halves are implemented. The journal keeps every intake record (option C, review-8). The accepted-order index is now live and bounded (option B): an entry leaves the index once it cannot still trade — no remaining amount, rejected by its own time-in-force, not resting in the open book, expired, nonce-cancelled, or epoch-invalidated — and `orderAccounts` prunes in lockstep so the state-root invariants hold. `orderReferenceSnapshot` now checks the durable evidence body-free (every marker has a receipt, a struct binding, and exactly one nonce claim; the receipt chain covers every marker) and applies the per-entry checks to the live subset only. The root derivation is versioned (`MATCHER_STATE_ROOT_VERSION`), so pruned and unpruned artifacts cannot be silently compared; artifacts binding an older root fail loudly at open. The trade feed reads taker sides from the durable journal records, the same binding account recovery already used, so executed trades survive body pruning. Cancelling an order that no longer has a body answers from the durable evidence: already-cancelled stays "already cancelled"; a filled, expired, or time-in-force-rejected order has nothing left to cancel. |
| review-8 | `persistent-store.ts` rebuilt the whole journal record array on every mutation with `[...this.#journal.records, record]`, so appending was O(n) and a store's lifetime cost was O(n squared). Measured in isolation, appending 2,000 records took 6.8ms from empty, 664.7ms from 40,000 existing, and 1,214.9ms from 90,000, against a configured `DEFAULT_MAX_JOURNAL_RECORDS` of 100,000. Every accepted order paid this, and it grew for the life of the process. | CLOSED. ADR 0010 is accepted and its journal half is implemented: the store keeps one records array for its lifetime and appends in place, making an append O(1) amortised. The aliasing decision is documented on the `journal` getter — `records` is a live reference that keeps growing, while `sequence`, `head` and `byteLength` are the values at the moment of the get — and a contract test fails if the array is rebuilt per append. `server.ts` reads `store.journal` fresh per request and is unaffected; no reader held a reference across a mutation. |
| review-6 | `src/lib/matcher-proxy.ts` carried a private 128-line copy of the strict JSON parser that `services/matcher/strict-json.ts` exports. Both sat on an ingress path and both were what stood between an untrusted request body and the matcher. A differential fuzz over 400,000 mutated documents, 103,825 of which both accepted, found zero divergence at the time, so this was a hazard rather than a defect: the two agreed, and nothing made them keep agreeing. | CLOSED. The canonical parser already lived on the matcher side of the boundary, so no closure change was needed: the proxy imports `parseStrictJson` from `services/matcher/strict-json.ts`, aliases its value type to `JournalValue`, and reduces its private copy to a wrapper that converts the parser's throw into the null its validation helpers branch on, passing the same explicit depth and node limits. The proxy defines none of the JSON grammar itself; a structural test in `matcher-route.test.ts` fails if a private copy returns. The matcher image's transitive source closure is unchanged because the import direction is proxy into services, not services into `src/lib`. |
| review-9 | CLOSED. The landing menu's hash links did not move focus to the section they named. `closeMenu()` closes a native `<dialog>`, and per spec that returns focus to the element which opened it, after the click handler returns. Focusing the target synchronously therefore looked correct and was undone a moment later, leaving a visitor who chose a destination from the menu back on the Menu button. Confirmed by reading `document.activeElement` after the click, which reported the Menu button at 0ms, 250ms and 1250ms. Deferring the focus by one animation frame lets the dialog finish its restoration first; the same probe then reports `section#markets`. | Closed. |
